Git 常用指令

从查看改动、分支开发到远程同步，按日常工作流程整理 Git 指令，并区分暂存、提交与撤销的边界。

阅读全文收起正文

先理解工作区、暂存区和本地仓库

工作区是正在编辑的文件；git add 将指定改动加入暂存区；git commit 把暂存区内容记录为本地提交。提交不会自动上传，推送到远程需要执行 git push。下面的仓库地址、文件路径和分支名均需按实际项目替换。

git clone <仓库地址>            # 克隆已有仓库
# 对没有仓库的新目录，可以改用 git init

git status --short              # 查看文件状态
git diff                        # 工作区与暂存区的差异
git diff --staged                # 暂存区与当前提交的差异
git log --oneline --graph -12    # 查看最近的提交历史
git show --stat HEAD             # 查看最新提交的文件统计

一次功能开发的常用流程

以下示例假设远程名为 origin、主分支为 main。执行前先确认当前分支和工作区状态；一条命令失败时应先处理原因，不要继续盲目执行后续步骤。

git switch -c feat/order-export
# 编辑业务代码后，明确选择需要提交的文件
git add src/OrderService.java
git diff --staged
git commit -m "feat(order): 新增订单导出功能"

git fetch origin
git merge origin/main
git push -u origin feat/order-export

fetch 更新远程跟踪信息，不会自动合并到当前分支；merge 才会整合指定分支。已配置上游时，git pull --ff-only 只接受快进更新，分支发生分叉会拒绝执行，此时按团队约定选择合并或变基。

临时保存与恢复现场

git stash push -u -m "临时保存导出功能"
git stash list
git stash apply "stash@{0}"

-u 包含未跟踪文件，但不包含被忽略的文件。apply 恢复后仍保留暂存记录；pop 在成功应用后还会移除对应记录。恢复时可能冲突，确认内容正确后再清理记录。

撤销前先区分要保留什么

  • git restore --staged 文件路径：取消暂存，保留工作区改动，适用于已有提交的仓库。
  • git restore 文件路径：用暂存区版本覆盖对应工作区文件，会丢失该文件尚未暂存的改动，必须先确认。
  • git revert 提交号：创建反向提交，通常适合撤销已共享的普通提交；合并提交需要另外明确主线。
  • git reflog：查看本地引用移动记录，有助于找回部分提交，但不是未提交文件的备份。
冲突处理顺序：查看 git status → 编辑冲突文件 → 暂存解决结果 → 按当前 merge 或 rebase 流程继续。不把强制推送、硬重置或批量清理当作默认解决方式，也不要把密码和密钥提交到仓库。

Git 提交描述符

理解 feat、fix、refactor 等提交前缀，让提交历史能够清楚说明改动目的、影响范围与不兼容变化。

阅读全文收起正文

描述符是一种协作约定

Git 本身不强制提交信息使用特定前缀。常见的 Conventional Commits 约定使用“类型 + 可选范围 + 描述”组织提交；团队可以通过检查工具约束格式，但安装 Git 并不会自动启用这些规则。

类型(可选范围): 简短描述

可选正文：解释为什么修改、采用什么方案。

可选页脚：关联问题、不兼容变更等信息。

常见类型及适用场景

  • feat：新增功能，例如增加订单导出接口。
  • fix：修复缺陷，例如修复分页条件丢失。
  • docs：文档修改，不涉及业务功能变更。
  • style：格式、空白或排版整理，通常不指新增界面功能。
  • refactor：重构内部实现，不以新增功能或修复缺陷为目的。
  • perf：性能改进，例如减少不必要的重复查询。
  • test：添加或调整测试。
  • build：构建系统、打包或依赖调整。
  • ci：持续集成、发布流水线配置。
  • chore：其他维护工作；revert：描述撤回某次改动。

除 feat、fix 与破坏性变更的约定含义外，其他类型的清单和版本发布映射需要由团队确定。不要把所有修改都写成 chore，也不要仅凭前缀认定功能已验证通过。

让标题表达具体动作

feat(order): 新增订单导出功能
fix(auth): 修复登录状态过期后重复跳转
refactor(user): 提取用户状态校验逻辑
docs(api): 补充分页参数说明
build(deps): 升级文档导出依赖

范围可以使用模块名，例如 order、auth、user。描述可以使用中文，重点是具体、可检索，避免“修改”“更新一下”“修复问题”等无法判断内容的表述。

如何描述不兼容变更

feat(api)!: 调整分页响应结构

统一列表接口的响应字段。

BREAKING CHANGE: 原 data 数组改为 data.items，客户端需同步调整。

! 或 BREAKING CHANGE: 页脚可标记破坏性变更，并不限定只能出现在 feat 中。是否自动生成版本号和变更日志，取决于项目工具配置。

一次提交尽量解决一个明确问题。业务功能、格式化和依赖升级混在一起时，即使前缀正确，也会增加审查与回退成本。已共享的历史不要为了改描述而擅自重写。

常用设计模式

从策略、工厂、模板方法到适配器和责任链，关注每种模式解决的问题，而不是为了使用模式增加抽象。

阅读全文收起正文

先找到变化点，再选择模式

  • 策略模式：将可替换的算法放在统一接口下，例如不同导出格式、计费规则或通知渠道。
  • 工厂方法：通过可扩展的创建方法决定具体产品。日常按类型选择实现的 Map 注册表或简单工厂，也能集中选择逻辑，但不等同于经典工厂方法。
  • 模板方法：固定流程骨架，将部分步骤交给子类，例如“读取 → 校验 → 转换 → 写入”的导入流程。
  • 建造者模式：分步骤组装复杂对象，改善参数多、可选项多时的可读性；构建前仍需验证必填项与约束。
  • 适配器模式：把第三方接口转换为业务需要的统一接口，隔离参数、返回值与异常差异。
  • 装饰器模式：保持接口不变，组合增加日志、计时等能力；装饰器的执行顺序可能影响结果。
  • 责任链模式：把多步校验或处理串起来，例如权限、参数、业务状态校验，明确失败后停止还是继续。
  • 观察者模式：事件发生后通知订阅者，适合解耦后续处理，但进程内事件本身不保证可靠投递。

策略与注册表：以文件导出为例

以下是 Java 17 风格的业务结构示意，省略 java.util 的导入和具体导出器实现。CSV、Word 等实现负责生成字节数据，服务只负责选择，不需要在多个业务入口重复判断类型。

interface Exporter {
    byte[] export(List<String> rows);
}

final class ExportService {
    private final Map<String, Exporter> exporters;

    ExportService(Map<String, Exporter> exporters) {
        this.exporters = Map.copyOf(exporters);
    }

    byte[] export(String format, List<String> rows) {
        Exporter exporter = exporters.get(format);
        if (exporter == null) {
            throw new IllegalArgumentException("不支持的导出格式");
        }
        return exporter.export(rows);
    }
}

调用方传入已注册的实现，例如 csv、word；入口应先校验 format 与 rows。新增格式时增加实现和注册项即可。Map.copyOf 固定的是映射关系，并不会让有可变状态的导出器自动变成线程安全。

单例、代理与 Spring 的关系

单例模式关注实例数量；Spring 的 singleton 通常指一个容器内某个 Bean 定义对应一个实例，并非整个 JVM 永远只有一个对象。单例 Bean 若保存请求级可变字段，仍然可能发生并发冲突。

代理模式通过代理对象控制访问，Spring AOP 常用它实现事务、拦截等能力。代理与装饰器结构可能相似，但关注点不同：前者侧重访问控制，后者侧重能力组合。

选择标准：是否确实存在多个变化方向？新增实现是否减少了对稳定代码的修改？只有一个简单实现时，可以先保持直观代码，避免提前引入庞大的继承体系。

Java 报错信息查看说明

读懂异常类型、Caused by、业务栈帧和行号，从完整日志定位原因，避免只凭最后一句提示修改代码。

先区分编译错误与运行异常

编译阶段的“找不到符号”“类型不兼容”优先查看源码位置、方法签名和依赖；运行时异常则需要完整堆栈、触发输入、运行版本和环境信息。应用启动失败时，日志末尾往往只是汇总，真正原因可能出现在更早的位置。

一段堆栈应该怎样读

org.springframework.beans.factory.BeanCreationException:
    Error creating bean with name 'orderService'
Caused by: java.lang.IllegalStateException: 无法加载业务规则
    at com.example.order.OrderService.loadRules(OrderService.java:42)
Caused by: java.io.FileNotFoundException:
    /opt/app/rules.json (No such file or directory)
    at java.base/java.io.FileInputStream.open0(Native Method)
    ... 18 more
  1. 最外层异常：说明失败发生在哪个框架或业务阶段。示例是 Bean 创建失败，不代表一定缺少注解。
  2. Caused by：向下追踪包装链。这里最深层已记录的原因是规则文件不存在，应核对配置路径、工作目录和容器挂载。
  3. 业务栈帧：找到自有包名和行号，例如 OrderService.java:42，并与实际部署版本对应。
  4. 省略行：... 18 more 表示与外层堆栈共享的尾部调用帧，不是另外发生了 18 个异常。

最深的 cause 只是当前日志记录到的底层异常，不一定能解释全部业务背景。还应查看同一请求前后的日志；Suppressed 则常表示资源关闭等过程中附加的异常，不能与 cause 混为一谈。

常见异常的排查方向

  • NullPointerException：确认具体哪个对象为空，再追踪数据为何缺失，不要只在每一层补空值判断。
  • IndexOutOfBoundsException：检查索引、集合长度及空结果；NumberFormatException：检查输入格式与取值范围。
  • ClassNotFoundException：检查目标类是否在运行时类路径；NoClassDefFoundError 还可能来自类初始化失败，应追查更早日志。
  • NoSuchMethodError：重点核对编译期与运行期依赖版本，以及实际部署包中的 JAR。
  • DataIntegrityViolationException：继续查看数据库原始错误，区分唯一键、非空、外键和长度限制。
  • BindException：检查监听地址和端口；连接超时则应分层检查网络、下游状态与超时配置。
  • OutOfMemoryError：先区分堆、元空间、直接内存或本地线程问题，不要一律通过增大堆内存处理。

记录异常时保留堆栈与上下文

下面是使用 SLF4J 的片段，假定 log、orderId 与业务方法已存在。最后一个参数传入异常对象，而不是只输出异常消息。

try {
    processOrder(orderId);
} catch (RuntimeException ex) {
    log.error("处理订单失败，orderId={}", orderId, ex);
    throw new IllegalStateException("订单处理失败", ex);
}
优先收集时间、请求标识、完整堆栈、关键输入和最近变更，并对密码、令牌和个人信息脱敏。同一个异常选择合适的边界记录，避免每一层重复打印；也不要捕获后返回成功，把真正的故障隐藏起来。

poi-tl 基础使用

用 Word 模板与 Java 数据生成文档，掌握文本占位符、图片渲染、资源关闭和常见依赖问题。

阅读全文收起正文

它适合解决什么问题

poi-tl 是基于 Apache POI 的 Word 模板引擎，适合生成合同、报告、通知等 .docx 文档。先在 Word 中设计排版并写入占位符，再用 Java 数据渲染；它不是通用 PDF 转换器，也不用于直接处理旧版 .doc 文件。

引入依赖并准备模板

下面采用 1.12.2 作为示例版本，并不表示它是最新版本。实际接入需要按项目 JDK、已有 POI 依赖及兼容要求选择版本，避免随意覆盖传递依赖。

<dependency>
    <groupId>com.deepoove</groupId>
    <artifactId>poi-tl</artifactId>
    <version>1.12.2</version>
</dependency>

在 Word 中新建 template.docx，写入以下文字，并保存到示例程序的工作目录。花括号使用英文半角字符，键名与 Java 数据保持一致。

{{title}}
姓名：{{name}}
岗位：{{position}}

渲染并输出文档

下面示例使用 Java 17。输出选择 CREATE_NEW，若 report.docx 已存在会报错，以免意外覆盖已有文件；重复运行时请使用新的输出文件名。

import com.deepoove.poi.XWPFTemplate;
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.HashMap;
import java.util.Map;

public class WordExportDemo {
    public static void main(String[] args) throws IOException {
        Map<String, Object> data = new HashMap<>();
        data.put("title", "人员信息表");
        data.put("name", "张三");
        data.put("position", "Java 开发工程师");

        try (InputStream input = Files.newInputStream(Path.of("template.docx"));
             XWPFTemplate template = XWPFTemplate.compile(input).render(data);
             OutputStream output = Files.newOutputStream(
                 Path.of("report.docx"), StandardOpenOption.CREATE_NEW)) {
            template.write(output);
        }
    }
}

图片、表格与循环不是同一种数据

普通文本使用 {{name}}。图片使用 {{@logo}}，对应数据可以通过 Pictures 构建；下面片段需要导入 com.deepoove.poi.data.Pictures，并在 render 之前放入 data。

data.put("logo", Pictures.ofLocal("logo.png")
    .size(120, 60)
    .create());

{{#table}} 通常用于表格渲染数据，应通过相应表格构建 API 准备数据；重复模板中的某一行则需要按版本配置循环行渲染策略。普通 List 不会自动适用于所有表格和循环场景。

接入业务时的注意事项

  • 模板放在 classpath 时通过资源流读取，不要假设打包后的资源仍是普通磁盘文件。
  • 每次请求使用独立的模板实例和输出流，不在线程之间共享正在渲染的 XWPFTemplate。
  • 占位符未替换时，核对模板、键名、语法和所在文档结构是否受当前版本支持。
  • 遇到 NoSuchMethodError 时检查 POI、XMLBeans 等依赖冲突；导出前限制模板、图片和批量数据的大小。
  • 下载响应使用正确的 .docx 内容类型与经过安全编码的文件名；不要直接信任用户提供的文件路径或远程图片地址。
示例模板和图片需要自行准备。生成 Word 与转换 PDF 是两个步骤；如果业务要求 PDF，需要额外的转换方案，并考虑字体、分页与部署环境差异。

Dockerfile 常用命令解析

区分构建阶段与运行阶段，理解 FROM、RUN、COPY、CMD、ENTRYPOINT 等指令，写出清晰的应用镜像定义。

阅读全文收起正文

Dockerfile 描述的是镜像如何构建

Dockerfile 是构建配方，镜像是构建产物，容器是基于镜像创建的运行实例。RUN 发生在构建阶段，不能代替容器启动时执行的 CMD 或 ENTRYPOINT。

  • FROM：指定基础镜像，也可以用多个 FROM 定义多阶段构建。
  • WORKDIR：设置后续指令的工作目录，优先使用明确的绝对路径。
  • COPY：将构建上下文中的文件复制到镜像，或使用 --from 从其他阶段复制制品。
  • ADD：在复制之外还支持特定来源下载、本地 tar 解包等行为；仅需复制时优先使用 COPY。
  • RUN：在构建阶段执行命令，例如安装依赖。不同 RUN 之间不会保留临时 shell 状态，切换目录优先用 WORKDIR。
  • ARG：声明构建参数；ENV：设置镜像环境变量，运行时可覆盖。两者都不适合保存密钥。
  • EXPOSE：声明应用预期端口，不会自动把端口发布到宿主机。
  • USER：设置后续构建指令与容器运行的用户；文件和挂载目录权限仍需单独配置。
  • ENTRYPOINT：定义主要启动程序；CMD：定义默认命令，或在与 ENTRYPOINT 配合时提供默认参数。
  • LABEL：添加镜像元数据；VOLUME：声明挂载点，实际数据持久化仍要规划卷与备份。
  • HEALTHCHECK：定义健康检查，检查程序必须存在于镜像中；健康失败本身不等于自动重启。
  • STOPSIGNAL：设置停止信号，仍需应用正确处理退出与平台停止超时。

一个 Spring Boot 运行镜像示例

假设已经构建好 Java 17 可执行 JAR，路径为 target/app.jar。以下 Dockerfile 使用 Linux 基础镜像，不会替你执行 Maven 构建。

FROM eclipse-temurin:17-jre
ARG APP_JAR=target/app.jar
WORKDIR /app
LABEL org.opencontainers.image.title="backend-api"
COPY --chown=10001:10001 ${APP_JAR} /app/app.jar
USER 10001:10001
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=60.0"
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
CMD ["--server.port=8080"]

这里的 CMD 是 Java 程序的默认参数。运行镜像时追加 --server.port=9090 会替换这些参数，但不会替换 ENTRYPOINT；若应用端口改变，端口映射也要同步调整。

CMD 与 ENTRYPOINT 的常见误区

JSON 数组是 exec 形式，不会自动执行 shell 的变量展开、管道或重定向。它能让主程序直接接收容器信号；shell 形式通常会经过命令解释器，需要额外关注信号转发。多个 CMD 不会依次执行，通常只有最后一个生效。

构建上下文、缓存与制品

docker build -t backend-api:1.0 .
docker build --build-arg APP_JAR=target/service.jar -t backend-api:1.1 .

末尾的点表示当前目录是构建上下文，不是 Dockerfile 所在路径的装饰。通过 .dockerignore 排除无关日志、IDE 文件和 .git，但不要排除需要 COPY 的 JAR。多阶段构建可以把编译工具留在构建阶段，仅把运行制品复制到最终镜像。

生产环境应评估并固定基础镜像版本或摘要，持续维护补丁。不要把凭据写入 ARG、ENV 或镜像层；构建时需要秘密信息应使用专门的 secret 机制。示例中的 JVM 内存比例也需要结合容器限额和非堆开销调整。

Docker 常用指令

按镜像、容器、日志、网络和数据卷整理常用命令，明确哪些操作只查看状态，哪些会停止服务或删除资源。

查看环境与镜像

docker version                    # 客户端与服务端版本
docker info                       # Docker 服务运行信息
docker image ls                   # 本地镜像
docker pull nginx:stable           # 拉取指定镜像标签
docker build -t backend-api:1.0 .  # 按当前目录的 Dockerfile 构建
docker system df                  # 查看 Docker 资源占用

客户端可用不代表服务端已经启动。镜像标签不是永久不变的内容标识，重复拉取同一标签可能获得新镜像；需要可重复部署时应管理具体制品版本或摘要。

创建与运行容器

假定 backend-api:1.0 已构建，应用在容器内监听 8080 端口。以下命令使用单行形式，可避免不同终端续行符的差异；资源数值仅为示例。

docker run -d --name backend-api --memory=512m --cpus=1 -p 127.0.0.1:8080:8080 backend-api:1.0
docker ps
docker ps -a

-d 表示后台运行；--name 指定名称；-p 按“宿主机地址:宿主机端口:容器端口”发布端口。这里绑定回环地址，仅供本机访问。应用不能只监听容器内部的 127.0.0.1，否则端口映射可能无法访问服务。

查看日志与运行状态

docker logs --tail 100 backend-api
docker logs -f --tail 100 backend-api
docker inspect backend-api
docker port backend-api
docker stats --no-stream backend-api
docker exec -it backend-api sh

logs -f 持续跟踪日志，在终端按 Ctrl+C 停止跟踪不会停止容器。exec 需要容器处于运行状态且包含对应程序，精简镜像未必带 sh 或 bash。不要把进入容器后手工修改文件当成正式发布方式。

停止、启动与删除

以下操作会改变服务状态，只应针对确认过的容器执行。停止和重启可能中断请求；删除容器会移除其可写层，重要数据应先确认已经持久化并备份。

docker stop --timeout 30 backend-api
docker start backend-api
docker restart backend-api

# 以下为单独的清理流程，确认不再需要后才执行
docker stop --timeout 30 backend-api
docker rm backend-api
docker image rm backend-api:1.0

stop 先请求正常退出，超过等待时间仍未结束时会强制终止；rm 不加强制参数时通常要求容器已停止。删除镜像可能因仍有容器引用而被拒绝，不应直接添加强制参数绕过保护。

网络、数据卷与 Compose

docker network ls
docker network inspect bridge
docker volume ls
docker volume inspect app-data

# 以下命令需要当前项目已有 Compose 配置
docker compose up -d
docker compose ps
docker compose logs --tail 100
docker compose down

app-data 是示例卷名，需要替换为实际名称。用户自定义网络中的容器可通过合适的服务名通信，容器内的 localhost 始终指向自身。compose down 会停止并移除项目容器与相应网络，默认不删除命名卷；不要随意附加删除卷的选项。

inspect 和日志可能包含环境变量、访问令牌或个人信息，分享前先脱敏。清理空间时先查看占用和引用关系，不把全局 prune 或强制删除作为第一步。

Java 多线程

并发、并行与任务的关系

并发表示多个任务在一段时间内交替推进，并行表示多个任务同时执行。线程共享进程内的资源，所以提高执行重叠度的同时，也引入数据竞争、调度和内存开销。

  • Thread：线程对象，调用 start() 才会启动新线程；直接调用 run() 仍在当前线程执行。
  • Runnable：没有返回值的任务；Callable<T>：可以返回结果并抛出受检异常的任务。
  • ExecutorService：管理任务执行；Future：获取任务结果、查询状态或请求取消。
  • CompletableFuture：组合多个异步阶段，例如 thenApply、thenCombine；阻塞型任务应使用适合的显式执行器。

用有界线程池执行任务

下面是 Java 17 的独立示例，参数仅用于说明机制。实际 Web 服务通常复用由应用生命周期管理的线程池，不应每次请求都创建一个新池。

import java.util.concurrent.*;

public class ThreadPoolDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2, 4, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(50),
            Executors.defaultThreadFactory(),
            new ThreadPoolExecutor.AbortPolicy());
        Future<Integer> future = null;
        try {
            future = pool.submit(() -> 1 + 2);
            System.out.println(future.get(2, TimeUnit.SECONDS));
        } catch (TimeoutException ex) {
            if (future != null) future.cancel(true);
            throw new IllegalStateException("任务等待超时", ex);
        } catch (ExecutionException ex) {
            throw new IllegalStateException("任务执行失败", ex.getCause());
        } catch (InterruptedException ex) {
            if (future != null) future.cancel(true);
            Thread.currentThread().interrupt();
        } finally {
            pool.shutdown();
            try {
                if (!pool.awaitTermination(3, TimeUnit.SECONDS)) {
                    pool.shutdownNow();
                }
            } catch (InterruptedException ex) {
                pool.shutdownNow();
                Thread.currentThread().interrupt();
            }
        }
    }
}

线程池通常先使用核心线程，再排队，队列满后才扩容到最大线程数，仍无法接收时触发拒绝策略。AbortPolicy 会抛出拒绝异常，提交方需要按业务处理繁忙状态。无界队列可能让最大线程数难以发挥作用，并积累过多待执行任务。

共享数据的三个关键问题

  • 原子性：count++ 包含读取、计算和写入，不是一个不可分割的操作；单个计数可考虑 AtomicInteger。
  • 可见性：一个线程的修改需要被其他线程可靠观察。volatile 能提供相应可见性和有序性约束，但不会让复合操作自动原子化。
  • 互斥与一致性：synchronized 或 Lock 可保护临界区；使用 Lock 时在 finally 中释放。多个字段必须一起更新时，单独使用几个原子变量未必足够。

异常、取消与上下文不能遗漏

submit 的任务异常通常保存在 Future 中，需要观察结果；Future.get 会用 ExecutionException 包装任务异常。cancel(true) 和 shutdownNow 主要通过中断请求协作停止，不保证强行终止所有任务；底层网络调用还需要自己的超时配置。

线程池会复用线程，ThreadLocal 用完后应按职责清理，不能假定上一次任务的值已经消失。普通线程绑定的事务、日志上下文和用户身份也不会自动正确传播。避免在同一个已被占满的线程池中提交子任务后再同步等待，以免发生线程饥饿。

先确定 CPU、数据库连接和下游接口能承受的并发量，再选择线程数、队列和超时。多线程适合可独立执行的工作，不适合通过增加共享可变状态来掩盖业务边界不清的问题。

Spring 事务管理的方式

比较声明式事务、TransactionTemplate 和底层事务管理器，理解传播行为、回滚规则及代理调用的适用边界。

先明确事务保护的范围

本地数据库事务用于让一组数据库操作一起提交或回滚。Spring 提供统一抽象，但实际能力取决于所选事务管理器和底层资源；一个普通数据库事务不会自动包含 HTTP 调用、文件写入或另一个独立数据源。

方式一：声明式事务

业务中最常见的是在服务方法上使用 @Transactional，让 Spring 在调用边界管理事务。以下示例省略导入，Order、Mapper 由业务项目提供，并且两个 Mapper 使用同一事务管理器管理的数据源。

@Service
public class OrderService {
    private final OrderMapper orders;
    private final AuditMapper audits;

    public OrderService(OrderMapper orders, AuditMapper audits) {
        this.orders = orders;
        this.audits = audits;
    }

    @Transactional(rollbackFor = Exception.class)
    public void create(Order order) {
        orders.insert(order);
        audits.record(order.getId());
    }
}

这里假设订单插入后能取得主键，审计记录也写入同一数据库。Spring Boot 在满足相关自动配置条件时通常启用事务支持；普通 Spring 配置可通过 @EnableTransactionManagement 启用，并提供适合的事务管理器。

声明式事务也可通过 XML 的 tx:advice 与 AOP 切点配置，适合某些传统项目的集中规则。注解与 XML 都是在声明事务边界，不是两套完全不同的数据库事务机制。

方式二：TransactionTemplate 编程式事务

当一个方法里只有一小段逻辑需要事务，或者边界由业务流程决定时，可以显式使用 TransactionTemplate。下例假定 transactionManager、Mapper 和 order 已由应用准备。

TransactionTemplate template = new TransactionTemplate(transactionManager);
template.setTimeout(10);

Long orderId = template.execute(status -> {
    orders.insert(order);
    audits.record(order.getId());
    return order.getId();
});

正常返回时模板尝试提交，运行时异常或 Error 通常触发回滚后继续抛出。若业务捕获了异常但仍要回滚，需要明确设置 status.setRollbackOnly()，并设计调用方能理解的失败结果。超时如何生效还依赖底层资源支持，不等同于强制停止任意 Java 代码。

方式三：直接使用事务管理器

通过 PlatformTransactionManager.getTransaction() 获取 TransactionStatus，再调用 commit 或 rollback，可以更直接地控制流程，但需要自己处理传播、异常与清理语义。多数普通业务优先选择注解或 TransactionTemplate，避免重复编写事务样板代码。

不要在 commit 已经失败后无条件再次 rollback；事务可能已完成，需遵循事务管理器的契约。响应式事务则通常使用 ReactiveTransactionManager 与 TransactionalOperator，不能直接套用线程绑定的命令式事务思路。

传播行为解决的是事务如何衔接

  • REQUIRED：有事务则加入，没有则新建，是常见默认值。
  • REQUIRES_NEW：使用独立事务，通常挂起外层事务；提交与回滚互相独立，还需要关注额外连接占用和锁等待。
  • NESTED：在支持的资源上使用保存点，不是独立提交，外层回滚仍会影响整体结果。
  • SUPPORTS：有事务则参与，没有也可执行；NOT_SUPPORTED：以非事务方式执行，必要时挂起当前事务。
  • MANDATORY：要求已有事务；NEVER：要求当前没有事务，否则报错。

常见失效与误解

  • 默认代理模式下，调用需要经过 Spring 代理。对象内部通过 this 调用另一个事务方法，不会触发该方法的事务拦截。
  • 自己 new 出来的对象不受 Spring 代理管理；private 方法不能靠常规代理织入事务，基于子类的代理也不能覆盖 final 方法。
  • 默认通常对 RuntimeException 和 Error 回滚，受检异常按业务需要配置 rollbackFor；异常被吞掉后正常返回，可能导致提交。
  • readOnly 通常是优化提示，不是普遍可靠的禁止写入机制；隔离级别与传播行为是不同维度，实际效果还受数据库和已加入事务影响。
  • 新线程不会自动继承普通线程绑定事务；多个事务管理器并存时，需要明确选择管理目标资源的那个。
长时间的远程请求和文件处理尽量不要包进数据库事务。提交后通知不等于可靠消息；涉及重要外部副作用时，仍需独立设计事件记录、重试与补偿。
